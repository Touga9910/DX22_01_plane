# Caromino 審査会改善対応 調査・改善計画（SE以外）

作成日：2026年11月04日

## 0. 調査範囲と結論

- 対象は現在の作業ツリーにあるコード、データ、テスト実行ファイル、直近のテレメトリ、戦闘UIキャプチャである。過去資料と差がある箇所は現在コードを優先した。
- SE関連のコード、アセット、調整値は調査・変更対象から除外した。
- 今回はソースコードを変更していない。本書だけを新規作成した。
- 最優先は「敵HP・敵意図・軸リソース変化・ショット結果」を一貫して読める状態にすることである。プレイヤーが結果の理由を理解できないまま数値調整を行うと、4軸の学習性とバランス評価の両方を誤る。
- 重量は演出・連鎖・テレメトリが最も進んでいる。一方、貫通・反射・アンカーはルール実装に対して専用Presentationと比較データが不足している。
- 攻撃予算とCharge妨害のルール／単体テストは成立している。ただし現行ステージデータでCharge可能敵の出現が確認できず、戦術としての成立は未確認である。
- Release x64通常設定は約60 FPSで安定しており、現時点で物理最適化を最優先にする根拠はない。新規VFXは既存プール・上限制御を再利用し、追加後の回帰だけを監視する。

### 分類

| 分類 | 意味 |
|---|---|
| 実装済み | 現在コード、現行データ、テストで主要経路を確認できた |
| 一部実装 | 基盤または一部表示はあるが、プレイヤーへの伝達が不完全 |
| 未実装 | 要求に対応するPresentationまたは経路を現在コードで確認できない |
| 要検証 | 実装はあるが、実戦データの量・条件が不足して効果を判定できない |

- 直近のRelease x64、1600×900、VSync、通常GameMCP publish間隔では平均59.998 FPS、p95 16.667 ms、p99 16.687 ms、最大16.758 ms。
- CPU平均はUpdate 0.629 ms、Draw 0.262 ms、Present 0.248 ms。物理は0.343 ms/step、51.113 ms/shot。

- 過去の約22 FPSはDebugかつGameMCPを毎フレームpublishした条件であり、通常Release性能の代表値ではない。
- GPU時間は独立計測されていない。現状は物理最適化より、新規VFX追加後のRelease回帰監視を優先する。

## 3. 優先順位と根拠

### P0：判断と検証を成立させる基盤

敵HP、敵意図、リソース増減、ショット結果、反射プレビューを先に行う。これらは「狙う理由」「成功した理由」「次のショットで使えるもの」をつなぐ情報である。数値を調整しても、この因果が見えなければプレイヤーは強さを理解できず、テスターの評価も安定しない。

同時にGameMCPの固定条件ベースラインを取り直す。UI/VFX追加は物理結果を変えず、バランス変更前後の比較点を保存する。

### P1：4軸の差別化と戦略性を作る

P0のイベントと表示を使い、貫通・反射・アンカーの専用演出を追加する。その後、同一シード・同一難易度で4軸と混成ビルドを比較する。重量の通常1ショット化、Chargeのコンテンツ不在、アンカー飽和、反射後空振りは、この段階でデータに基づき調整する。

### P2：豪華さと将来最適化

大規模な画面演出やGPU詳細計測は、P0/P1の視認性と比較結果が安定してから行う。現時点で物理CPU負荷は優先課題ではない。

## 4. 各項目の具体的な実装方針

### 4.1 Presentation用イベントを既存経路へ追加する

新しいManager／Singletonは作らない。既存の `GameEvent` と `Game::PublishGameEvent` 経路へ、値だけを持つ次のイベントを追加する。

- `AxisResourceChangedEvent`：軸、所有者、変更前後、増減理由、上限到達、消費先。
- `AxisAbilityTriggeredEvent`：軸、能力種別、発生位置、対象、強度／段階、フィニッシャーか。
- `ShotResolvedPresentationEvent`：命中、合計ダメージ、撃破、Charge中断、軸ごとの獲得／消費、フィニッシャー、ショット時間。
- 必要な場合だけ `EnemyIntentPresentationEvent`：行動、対象、Charge段階、予測ダメージ。Plannerの内部状態を直接描画側へ公開しない。

責務は次の一方向に保つ。

`Physics / Rules → 値イベント → Gameの既存ルーティング → GamePresentation / CollisionVfxSystem`

Presentationから物理状態を書き換えない。イベント追加前後で固定ショットの物理・ダメージ・乱数結果が一致することを必須とする。

### 4.2 敵HPと敵意図

- `GamePresentation` の既存敵ステータス描画へ、敵ごとの画面空間HPバーを統合する。
- 現在HP／最大HP、25%・50%の色変化、撃破予定状態、選択／Charge中の強調を表示する。
- HP、意図、状態異常、アンカースタックを同じレイアウト計算へ渡し、別々に重ならせない。
- 攻撃意図は既存「待・攻・溜・強」バッジを拡張し、対象アイコン、解決順、Charge段階、妨害可能条件を短く示す。
- 通常攻撃が常にプレイヤー対象なら常時長い線は出さず、対象アイコンまたは短い方向マーカーを使う。特殊対象がある場合のみリング／線を出す。
- ホバー詳細は補助情報とし、戦闘判断に必須なHP・行動・Charge段階は非ホバーでも読めるようにする。

### 4.3 スタック変化・ショット結果・数字整理

- スタック獲得時は対象位置からHUDバッジへ小さなパルス／ピップ移動、消費時はバッジから能力発生位置へ逆方向の移動を使う。
- 1回のショット内で同種増減が多い場合は個別表示せず、短い時間窓で `+N` / `-N` に統合する。
- ショット終了後に1.2～1.6秒のコンパクトな結果パネルを表示し、命中、ダメージ、撃破、Charge中断、軸増減、フィニッシャーだけを優先度順に出す。
- ダメージ数字は「同一対象＋同一衝突エピソード」で統合し、画面領域／対象ごとの同時表示数を制限する。省略分はショット結果へ集約する。
- 優先順位は `プレイヤーダメージ／撃破 > フィニッシャー > 能力発動 > 強衝突 > 弱衝突` とする。
- HP・意図・照準経路を保護領域へ追加し、VFX・数字の配置候補から除外する。

### 4.4 4軸VFX（既存VFX基盤を再利用）

| 軸 | 通常→強化の差 | 発動／蓄積 | フィニッシャー | 再利用先 |
|---|---|---|---|---|
| 重量 | 衝撃波半径、破片量、色温度、短い揺れを段階化 | 既存3/6/10/15段階へ獲得・消費パルスを接続 | 既存大連鎖表現を開始／完了で明確化 | Spark / Shockwave / Burst、CHAIN UI |
| 貫通 | 紫の方向性スラッシュと入口→出口ライン | トレース設置時の短い残光、再利用時の点灯、ミニオン発射線 | 複数トレースが対象へ収束する演出 | Trace描画、Burst、既存軌跡 |
| 反射 | 壁法線に沿う黄色リップル、反射回数に応じた尾 | クッションChargeを既存表示から命中パルスへ接続 | ピンボール対象の輪郭と反射経路を順番に点灯 | WallImpact、Shockwave、TableFrame表示 |
| アンカー | 青緑のロックリング／短いテザー | 敵付与、5:1変換、盾消費、帰還をピップ移動で表現 | 全スタックを中心へ引き込み、結果だけ強い一波にまとめる | Chain ring、Burst、状態バッジ |

大連鎖の盛り上がりは軸共通の段階値を使うが、見た目は各軸固有にする。弱い段階は盤面情報を優先し、3でバナー、6で色／粒子追加、10で短い揺れ、15で最終アクセントという既存重量の考え方を一般化する。全段階でプール上限を超えない。

### 4.5 反射プレビュー

- `SharedShotPrediction` が返す `reflectionPathIndices` とプレビュー点列を利用し、最初の1反射までを表示する。
- 直線部分は現行表示、反射後は色／点線を変え、「予測であり保証ではない」ことを視覚的に区別する。
- 2反射目以降は当面表示しない。全経路を見せて照準を自動化せず、反射軸の基本操作だけを支援する。
- 描画追加のみとし、実射物理・反射係数・停止判定は変更しない。

### 4.6 バランス検証

GameMCP復旧後、`standard / heavy / pierce / bounce / anchor` の既存ビルドプロファイルを使用し、同一シード、同一難易度、Dynamic Balance無効で比較する。

1. 探索計測：各プロファイル10有効ラン以上。極端な不具合とテレメトリ欠落を検出する。
2. 正式計測：既存基準の通常30、ミッドボス15、ボス10以上を満たす。
3. 人間確認：初心者・中級者・上級者で、UI理解、照準意図、成功理由を確認する。
4. 固定ショットA/B：数値変更前後で同一初期状態を再生し、変化したルールだけを特定する。

軸別に追加／集計する指標は以下とする。

- 重量：敵対敵衝突、ユニーク衝突ペア、連鎖距離、生成／消費／上限超過、通常1ショットクリア率。
- 貫通：貫通対象数、トレース設置／再利用、ミニオン有効攻撃数、空振り、フィニッシャー支払い。
- 反射：反射回数帯、反射後の有効攻撃率、生成／消費、ピンボール発動／空振り、フィニッシャー。
- アンカー：敵／プレイヤー生成、5:1変換、盾吸収、帰還、消費、フィニッシャー回数／ダメージ、上限滞在率。
- 混成：単軸からのダメージ、撃破、必要ショット数、有効攻撃率の増減。強いだけでなく、照準選択が変わったかを記録する。

調整の初期ガードレールは以下とする。データ取得後に最終値を確定する。

- 通常戦のショット中央値を既存目標3～5へ戻し、1ショット全滅率を補助指標として監視する。
- ボス中央値7～12を維持し、無命中率が高い場合はHPより配置・当たり方・情報提示を先に疑う。
- フィニッシャーは前提パーツ取得後の該当軸ショットで「一度も出ない／ほぼ毎回出る」の両極を避ける。暫定観測帯は15～35%とし、楽しさの人間評価で確定する。
- 敵種×軸で、意図したカウンター説明なしに必要ショット中央値が1.5倍以上偏る組合せを残さない。
- 混成ビルドが単軸を恒常的に大幅上回る場合、単なる倍率相乗ではなく照準・配置選択を要求しているかを確認する。

### 4.7 敵システム

- 攻撃予算はまず変更せず、計画予算、実消費、Wait理由、行動可能敵数、予約、解決順をランごとに記録する。
- `enemy_striker` を含む固定検証レイアウトを用意し、Charge開始→妨害機会→成功／失敗→強攻撃までを再現する。
- 重量、貫通、ポケット、撃破の4妨害手段が、少なくとも1つは現実的な照準で成立することを確認する。
- 密集、直線、散開、壁際、Charge護衛の同一HPレイアウトを作り、選択球・角度・対象順が変化するかを比較する。
- 敵種×4軸マトリクスで、ダメージ、有効命中、撃破ショット数、無命中率を取得する。
- 大連鎖対策は即座に一律耐性を付けない。まず重複密集レイアウト、連鎖距離、スタック上限、報酬量のどこが原因かを切り分ける。

### 4.8 パフォーマンス

- 新規VFXごとに既存固定ショットをRelease x64でA/B実行する。
- 完了目安は1600×900、VSyncで平均59.5 FPS以上、p95 16.8 ms以下、p99 17.5 ms以下、追加Draw CPU 0.5 ms以内とする。
- VFX有無で物理結果、ダメージ、撃破、乱数系列が一致することを確認する。
- 上限到達時は弱いVFXから省略し、HP・意図・フィニッシャー結果を残す。
- この基準を外れた場合だけGPU計測や個別VFX削減へ進み、物理最適化は最後にする。

## 6. 検証方法と完了条件

### 6.1 UI・視認性

- 1、4、8、12体の敵、通常／Charge／状態異常／アンカーを含む固定シーンを1600×900と1280×720でキャプチャする。
- 全生存敵のHPと次行動が非ホバー状態で識別できる。
- HP、意図、状態、照準線がダメージ数字やVFXに恒常的に隠れない。
- 大連鎖時も撃破、プレイヤーダメージ、フィニッシャー、ショット合計が読める。
- 色だけに依存せず、文字／形／アイコンで4軸とCharge段階を区別できる。
- 5人程度の初見確認で「どの敵を狙うか」「何が増減したか」「ショット結果」を口頭説明できる。

### 6.2 4軸VFX

- 各軸で通常、強化、獲得、消費、フィニッシャーの固定キャプチャを作る。
- 同じ汎用スパークだけでなく、静止画でも軸を識別できる。
- 大連鎖で段階が上がる一方、弱い衝突を省略して盤面情報を維持する。
- VFX有無で固定ショットの物理結果が完全一致する。

### 6.3 バランス

- GameMCP／C++ AIの同一シード比較を保存し、プロファイル、難易度、ビルド、設定ハッシュをログへ残す。
- 通常30、ミッドボス15、ボス10以上の正式サンプルを満たす。
- 4軸すべてで、発動率、生成／消費、空振り、有効攻撃、フィニッシャー到達を欠損なく集計できる。
- 重量の通常1ショット率、反射回数帯別成功率、貫通トレース再利用率、アンカー上限滞在率について、調整前後を比較できる。
- 自動AIの勝率だけで完了にせず、人間が照準意図と成功理由を理解できることを確認する。

### 6.4 敵システム

- 全計画で攻撃予算上限を超えず、予約と公平性テストが合格する。
- Chargeの開始、妨害成功、妨害失敗、強攻撃解決を固定レイアウトで再現できる。
- 同一ビルドでも配置差により、選択球・角度・最初の対象の少なくとも1つが合理的に変化する。
- 敵種×軸マトリクスに、説明できない恒常的な1.5倍超の不利が残らない。

### 6.5 性能・回帰

- Release x64で平均59.5 FPS以上、p95 16.8 ms以下、p99 17.5 ms以下。
- 新規VFXの追加Draw CPUは固定条件で0.5 ms以内。
- VFX上限、マージ、スキップが大連鎖で作動し、無制限増加しない。
- 現行C++テスト群がすべて合格し、Python環境を用意した後にPythonテストも実行する。
- SE関連ファイルに差分がない。

## 7. 推奨する開発順序と依存関係

| 順序 | 作業 | 依存／出口条件 |
|---|---|---|
| 1 | 現行テレメトリの凍結、GameMCP接続復旧、固定シード基準ラン | バランス変更前の比較結果を保存 |
| 2 | 軸増減・能力・ショット終了のPresentationイベント定義 | 物理結果不変、イベント順テスト合格 |
| 3 | 敵HP、敵意図、Charge段階、ショット結果パネル | 固定UIシーンで非ホバーでも判断可能 |
| 4 | 数字統合、保護領域、VFX優先順位 | CHAIN 10以上でも盤面と結果が読める |
| 5 | 最初の1反射プレビュー | 共有予測と実射の一致テスト合格 |
| 6 | 貫通・反射・アンカーの専用VFX、重量の不足分 | 4軸の固定キャプチャと性能基準合格 |
| 7 | 4軸単独プロファイルの探索／正式比較 | 指標欠損なし、必要サンプル数達成 |
| 8 | 重量、貫通、反射、アンカーを原因別に調整 | 目標帯と人間評価の両方を満たす |
| 9 | Charge敵・配置多様性・敵種×軸を調整 | 予算・妨害・選択変化の完了条件達成 |
| 10 | 混成シナジーと全軸フィニッシャー頻度を調整 | 単軸を無意味にせず照準選択が増える |
| 11 | Release性能回帰、全テスト、審査用キャプチャ | 60 FPS、物理不変、SE差分なし |
| 12 | P2の豪華演出／GPU詳細計測を必要に応じて実施 | P0/P1完了後のみ |

依存関係の要点は、`可観測性 → 専用演出 → 定量比較 → ルール／配置調整 → 最終演出と性能確認` である。UIとログが不足した状態で先に数値を変更しないこと、またPresentation改善を物理・ルール変更と同じ差分へ混ぜないことを推奨する。
