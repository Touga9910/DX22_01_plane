# Caromino Debug / Release性能比較とCPU Updateボトルネック調査

作成日：2026年11月3日

結論
====

直近の約22 FPSはゲーム本体や追加VFXの負荷ではなく、性能検証用コピーの
game_mcp_bridge.jsonがstate_publish_interval_frames=1となり、巨大なGameMCP状態を
毎フレーム生成・JSON化・書き出ししていたことが主原因だった。

前回条件を再現したDebug x64では平均23.52 FPS、CPU Update平均40.92 msであり、
GameMcpBridge::UpdateがUpdate時間の85.94%を占めた。Release x64では同じ毎フレーム
公開条件でも平均59.92 FPSまで改善した。

通常プロジェクト設定のstate_publish_interval_frames=60では、Release x64は
平均59.998 FPS、p95 16.667 ms、p99 16.687 msで安定して60 FPSを達成した。
CPU Update平均は0.629 ms、CPU Draw平均は0.262 msである。

固定物理は149ステップで全構成一致した。ReleaseのBallPhysicsWorld::Stepは
1ステップ平均0.343 ms、1ショット合計51.113 msであり、2.483秒のショット全体へ
分散して実行される。捨て時間は0秒、最大でも3ステップ/描画フレーム
（毎フレームMCP公開時Debugのみ最大4）で、上限8には一度も達していない。
固定更新の複数実行は遅いDebugフレームの結果であり、負荷を暴走させる主原因ではない。

Releaseの通常プレイ性能を理由に物理最適化を先行する必要はない。戦闘SE実装へ進んでよい。
先に直す価値があるのは、性能検証用コピーがGameMCPを毎フレーム公開しないようにすることと、
開発用MCPの状態生成スパイクを必要に応じて軽量化することである。


A. 調査概要
============

目的
----

- 約22 FPSがDebug固有か、Releaseでも再現するかを実測する。
- CPU Update約43 msの処理単位を、重複しない上位区間へ分割する。
- 固定物理のステップ数、処理時間、捨て時間、描画フレームとの関係を確認する。
- 物理やVFXを変更せず、次に最適化すべき対象を判断する。

プレイヤーに見える変化はない。選択・狙い・連鎖、物理結果、VFXの見た目は変更していない。
成功条件はDebug/Releaseの同一物理結果、実測内訳、計測OFF時の非介入を確認できることとした。

--------

- PC：WIN11OHS40236
- CPU：13th Gen Intel(R) Core(TM) i7-13650HX、20論理プロセッサ
- OS：Windows NT 10.0.26200.0、x64
- API：DirectX 11
- GPU：同一PC・同一GPUで全測定を連続実施。GPU時間とGPU型番は今回のCPU計測には含めていない。
- 解像度：1600×900、ウィンドウモード
- VSync：有効、Present(1, 0)
- 描画：実描画あり。スクリーンショット、録画は計測中に実施していない。
- 時計：std::chrono::steady_clock

算出方法
--------

- 平均フレーム時間：ショット計測区間の描画開始間隔の算術平均。
- 平均FPS：1000 / 平均フレーム時間。
- p95/p99：各回の昇順フレーム時間に対するnearest-rank。表は5回の値の算術平均。
- 最大：5回中の最大値。
- 1% Low相当：1000 / p99。実フレーム列の最遅1%平均ではなく、p99の逆数。
- ショット時間：計測対象フレーム時間の合計。

前回再現条件の主因
------------------

- Debug GameMCP：1ショット2096.020 ms、1呼出平均35.168 ms、Updateの85.94%。
- Debug 固定物理：1ショット247.171 ms、1描画フレーム平均4.147 ms、Updateの10.13%。
- Release GameMCP：1ショット650.704 ms、1呼出平均4.361 ms、Updateの87.85%。

GameMCPの割合が大きいのはstate_publish_interval_frames=1により、BuildState、GameMcpReadView::Capture、
多数の配列構築、JSONシリアライズ、ファイル置換を毎フレーム行ったためである。

予測・照準
----------

ショット中はBattleState::BallsMovingであり、PlayerBall::GeneratePreTrajectoryは0回だった。
計測されたshot_predictionはDebug/Releaseとも0 ms、0回である。今回の約43 msの原因ではない。

E. 負荷の主原因
================

実測で確認できたこと
--------------------

1. 約22 FPSの直接原因は性能検証用のGameMCP毎フレーム状態公開である。
2. Debugの未最適化コードがBuildState/JSON処理を35.17 ms/回まで増幅した。
3. Releaseでは同じ処理が4.36 ms/回となり、毎フレーム公開でもほぼ60 FPSだった。
4. 通常公開間隔ではRelease Update 0.629 ms、Draw 0.262 ms、Present 0.248 msで安定60 FPSだった。
5. Presentation更新はReleaseで平均0.0058 ms/呼出、Draw全体も0.262 msで、VFXは主因ではない。
6. 予測線はショット中0回で、原因ではない。
7. 固定物理はDebugでは相対的に重いが、Releaseでは1ステップ0.343 msで問題化していない。

仮説に留まること
----------------

- BallPhysicsWorld内部のTOI探索、接触解決、環境解決のどれが51.1 ms/shotの中心かは未分割。
  Releaseの絶対負荷が小さいため、今回はさらにタイマーを挿入していない。
- GPU時間は測っていない。Present時間が小さく、CPU Drawにも余裕があるが、CPU測定だけで
  GPUボトルネックが存在しないと断定はしない。

H. 今後の推奨作業
==================

1. Releaseで60 FPSを安定達成できているか
   達成している。通常MCP間隔で平均59.998 FPS、p99 16.687 ms、最大16.758 ms。

2. 達成できていない場合の主因
   該当しない。前回約22 FPSの主因は毎フレームGameMCP公開とDebug最適化不足の組合せ。

3. 最初に最適化すべき関数・ファイル
   通常ゲームの最適化は不要。開発時のスパイクを直すならGameMcpBridge.cppの
   BuildState、PublishStateとGameMcpReadView::Captureを最初に扱う。

4. 期待できる改善
   公開間隔を通常値へ戻した診断比較ではDebug平均23.52→58.35 FPSとなった。
   キャッシュ等の未実装最適化について具体的な改善率は未計測のため断定しない。

5. 次のVFX・SE開発へ進んでよいか
   進んでよい。Release CPU Update/Drawには十分な余裕があり、VFX更新・描画は主因ではない。
   就職作品の説明では「Debugの22 FPSを物理負荷と決めつけず、Release比較と区間計測で
   開発用MCPの毎フレームJSON公開を特定し、決定的物理を変更せず解決方針を選んだ」と説明できる。
