自動プレイ連続実行時の保持データ調査

目的・範囲
同一processで最大50runを実行する補助観測に先立ち、GameMcp、BalanceLogger、弾道予測、物理・診断履歴の生存期間をソースから確認した。対象ソースは本資料の親ディレクトリ直下の DX22_01_plane/。この調査ではコード変更、ビルド、ゲーム起動、resource observerへの取付けを行っていない。実測によるleak判定や、過去の途中終了原因の推定ではない。

1. GameMcp：process内には最新状態のみ
GameMcpBridge.h の保持情報は状態sequence、最後のcommand ID、enemy catalog等。GameMcpBridge.cpp の Initialize はcatalogを再作成し、PublishState→BuildState（GameMcpStateSerialization.cpp）は呼出しごとに一時JSONを構築する。ProcessPendingCommandもコマンド履歴を蓄積しない。WriteJsonAtomicallyは局所ofstreamで最新の game_state.json／last_result.json を置換する。完了runごとのsnapshot配列は見つからなかった。sequence値の増加は保持サイズの増加ではない。

2. BalanceLogger：現在runの詳細は増えるが、次runで置換
BalanceLogger.cpp の BeginRun は m_Root 全体を新しいJSONへ置換し、latest telemetry 4種とcollectorをresetする。EndRun後には最後のrunが次のBeginRunまで残る。BalanceLoggerStage.cpp の BeginStage、BalanceLoggerShot.cpp の EndShot、BalanceLoggerEvents.cpp の Record系は、現在runの stages／shots／events等へ追加するため、1runが長いほどliveデータは増える。完了した全runのメモリ内archiveは見つからなかった。
ShotPhysicsTelemetry.h の Reset、PierceAttackTelemetry.h の BeginShot／Resetでshot用vector／mapをclearする。BalanceLoggerShot.cpp の BeginShotもpending shotとbounce集計を初期化する。現在shotのcollision／wall reflection／timelineには件数のhard capがなく、長いshotや衝突の多いshotでは増える。run_*.jsonはrun数に応じてディスク上で増えるが、BalanceLoggerStorage.cpp の Saveは局所streamを閉じる構成。

3. 弾道予測：一時結果または1件cache
GameBattleBridge.cpp の MakeShotPredictionInputとGameShotPrediction呼出しは局所入力・結果を使う。BallShotPrediction.cpp は最大1200ticks／経路1000点、BallTrajectoryPreview.cpp は最大1200ticks／1tick接触32回／経路1000点。PlayerBall.cpp の GeneratePreTrajectoryは現在のpreviewを更新し、PlayerBall.hは通常previewと最大威力preview各1件を保持する。通常移動のtrailは144点まで。これらはPlayerBall componentの寿命に属し、run別cacheではない。
BossShotPlanner.h／GameBossAI.cpp の EvaluateはkeyとJSON各1件を保持する。候補はoffer当たり最大128件を評価し、公開する代替案はoffer当たり最大12件。boss不在時は前の結果が残り得るが、runごとに追加するmapではない。入力のoffer数・盤面サイズに応じた1件分のサイズは変わる。

4. 物理・診断履歴：固定長または現在盤面に従う
GameRuntimeState.h／.cpp のframe timingは512件、aiming timingは300件の固定配列ring。BattleController.cpp の SetStateは履歴12件、GameDebugForecast.cpp の RecordPlayerDamageは10件まで。RefreshCombatForecastは現在敵一覧から1件のsnapshotを作って置換する。
BallPhysicsWorld.cpp の Stepはworld adapter／body配列を局所作成する。BallCollisionComponent.cpp の ResetShotAbilityStateはshot開始時の接触集合をclearし、ForgetMissingContactsは現在のactiveBallsにない参照を除去するため、接触集合は現在盤面に従う。
通常のscene objectはSceneManager.cppの旧scene破棄→StageBase.cppのUninitによるDestroy要求を経て、Game.cppのUpdate先頭・後半のGameWorld::RemoveDestroyedでunique_ptrごと消去される。PierceMinionは停止・pocket時およびGameShotEnd.cppのshot終了処理でもDestroyされる。これは確認した通常経路の説明であり、全object種・全中断経路の網羅的な寿命証明ではない。

観測時の読み方・限界
上記対象では「完了run数に比例するメモリ内履歴」は見つからなかった。一方、vector.clear／unordered_map.clear後のcapacityやbucket、GameWorld配列の過去ピーク、allocatorの解放待ちにより、live要素を消しても使用メモリが直ちに低下するとは限らない。同じscene・shot境界で、run内のstage／shot／event数や盤面規模を揃えて推移を見る必要がある。
raw MCP JSONL、balance JSON、native診断JSONLは時間・run数に応じたディスク増加であり、外部Python observerのメモリとも区別する。D3D／GPU driver、audio、texture／model／asset cache、allocator内部、全object種の登録漏れは今回の網羅調査対象外。使用メモリやhandle数の増加だけでleakや元の終了原因と断定しない。resource observerの確定版は変更していない。
