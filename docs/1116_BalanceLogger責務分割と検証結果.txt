BalanceLoggerの責務分割と検証結果

実装前の方針

プレイヤーに見える変化：ゲームの挙動・数値・ログ形式を維持する。
守る柱：選択・狙い・連鎖の結果を観測する記録処理を読みやすくする。
取得前後・強化前後の狙い：今回の分割ではゲームの判断や成長を変更しない。
危険と対策：集計順、未観測値のnull、同一targetの重複排除、保存タイミングを
変えない。公開APIと状態を保ち、固定イベント列の出力JSONを前後で比較する。
成功条件：長いEndShot自体も責務別の処理へ分け、関連テストを通す。
PCH有効のDebug/Releaseクリーンビルドを前後各3回計測し、高速化の維持を確認する。

BalanceLogger.cppを2,039行から244行へ分割した。

イベント集計と結果のJSON反映を内部helperへ分けた。
追加は実装8本、内部ヘッダー2本。分割後の実装で最長は353行。
公開BalanceLogger.h、Gameの実装、両telemetry collector、PCHは変更していない。

今回の測定では両構成とも少し増加したが、PCHによる高速化の水準はほぼ維持した。

2. 熟読して把握した構成

Game側はラン開始、ステージ開始、ショット開始でloggerへ初期値を渡し、
物理・敵・球種効果がRecord*へ観測事実を送る。loggerはゲームの挙動を決めず、
ショット／ステージ／ランの境界で集計・保存する。
GameMcpCombatStateは最新ショット4種のJSONを読み、Pythonの解析・比較・収集処理は
保存されたschema version 4のログを読む。

元EndShotは次のすべてを一つの関数で行っていた。
・衝突数とダメージの確定、スコア算出
・物理と攻撃collectorを確定し、JSONへ変換
・shot_eventsから球種スタック、反射、盤面効果、防止ダメージを集計
・AI予測と実績をdecision_logへ書く
・各球種のスタックと最新MCP向け情報を更新
・ステージへショットを追加し、状態を解除して保存

このうちイベントの意味を読む計算と、永続化する状態の更新は変更理由が異なる。
またRecord*は直前の衝突種別や反射timelineを共有するため、観測APIごとに別の
状態を持たせる分割は不適切と判断した。

3. 分割の判断理由と構成

一つのBalanceLoggerが状態を所有する設計と公開APIを維持し、実装を責務別に分けた。
ヘッダーを変更しないことで、利用側へ新しい内部型を広げず、既存の呼び方も保つ。

ファイル                         行数  責務
BalanceLogger.cpp                244  singleton、ラン開始・終了、現在stageの取得
BalanceLoggerStage.cpp           243  stageの開始・終了とステージ全体の要約
BalanceLoggerShot.cpp            245  shot開始、確定の処理順、スコア算出
BalanceLoggerEvents.cpp          353  Record*観測API、衝突文脈とtimelineの更新
BalanceLoggerShotEvents.cpp      262  shot_eventsから集計値を作る計算
BalanceLoggerShotResults.cpp     217  decision_logとheavy/pierceの結果反映
BalanceLoggerTelemetryJson.cpp   341  physics/pierce/bounceのJSON変換と丸め処理
BalanceLoggerStorage.cpp         125  保存、時刻、run ID
BalanceLoggerConfiguration.cpp   135  metadata、設定snapshot、ファイルfingerprint

内部ヘッダー：
・BalanceLoggerShotSummary.h（68行）
  ShotEventSummaryにイベント集計値とtarget別の防止量をまとめる。
  ShotCompletionFactsは既に確定したダメージ・撃破数などの値だけを渡す。
  ReflectionStackSummaryは計算後の反射スタックとfizzleを返す。
  大量の引数や新しい内部JSONキーで処理同士を結び付けず、必要な値を型で渡す。
・BalanceLoggerTelemetryJson.h（41行）
  共有するJSON変換と丸め処理だけを宣言する。共通のpierce集計変換は
  実装ファイル内のanonymous namespaceへ残す。

EndShotは「基本結果確定→collector確定→イベント集計→decision反映→stack反映
→bounce変換→latest更新→stage追加→状態解除→Save」を追える入口にした。
保存・metadataの変更、球種集計の変更、JSON形式の変更を別々の実装で読める。
PCHへゲーム固有のヘッダーは追加せず、各.cppを独立してコンパイルする。

4. 維持した不変条件

・当たったがダメージを観測していない場合はnull。衝突なし／既知の0と区別する。
  stage内に不明なshotがあるとstage集計をnullにする既存仕様も維持。
・collision_effectはplayer衝突数＋enemy衝突数×2。スコア式と小数2桁の丸めは不変。
・防止ダメージは同じtarget内の最大値を採り、次ターンと将来のチャージを別に集計。
・heavy旧イベントのfallback、pierceの上限、反射スタック上限のnullを維持。
・壁と攻撃のtimeline順、target index、physics stable indexを作り直さない。
  empowered bonusは次の該当targetで一度だけ消費し、特殊ダメージは直前の攻撃を修飾。
・RecordPierceAttackはcollectorへ転送してからactive判定する順序を維持。
・BeginRun/BeginStageでlatest4種を消去し、BeginShotでは前shotのlatestを保持する。
・RecordEvent/RecordPlayerDamageはdirtyにするだけ。BeginShot前に前回分をflushする。
・EndStageはactive shotを先に確定してstage参照を取り直し、EndRunは保存後に解除する。
・Saveは成功したときだけdirtyを解除。一時ファイルの書込み、既存ファイルの削除、
  renameという従来の方式・失敗時処理も変更しない。
・run IDはlocal time、記録日時はUTC。managed_filesの順、FNV-1a64、欠損file表現は不変。
