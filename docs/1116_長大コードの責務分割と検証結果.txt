1. 実施結果

構成、状態の所有者、呼び出し順、既存の分割方針、テスト、ビルド設定を
確認したうえで、責務混在が特に大きかったGame.cppとGamePresentation.cppを
中心に分割した。

  Game.cpp：4,205行 → 518行
  GamePresentation.cpp：5,568行 → 388行

新規の本体実装33ファイル、専用ヘッダー4ファイルをプロジェクトと
Visual Studioのフィルターに登録した。Gameの公開APIと状態の所有構造は
維持しており、Game.hに変更はない。

2. 実装前に定めた目的と成功条件

プレイヤーに見える変更：既存の画面、操作、戦闘結果を維持する。
守る柱：選択・狙い・連鎖を支えるゲームルールの再現性を保つ。
取得前後・強化前後の狙い：今回の整理によって変化させない。
危険と対策：更新、乱数、イベント、描画の順序を変えると連鎖や演出が変わる
ため、既存処理の移動と順序を保つ抽出を基本にする。
成功条件：責務の所在が名前から追えること、編集時に再コンパイルする範囲を
狭めること、Debug/Release・関連テスト・実ゲームのショット進行を確認すること。

3. 読み取りで把握した構成

Gameは既に、GameWorld、RunController、BattleController、GameRuntimeState、
各種ラン状態・保存状態へ所有責任を委譲していた。
一方で、Game.cppにはそれらの操作のほか、GameRuntimeの入口、診断予測、
カード画像のGPU管理、カード・ポーズ・報酬の描画まで残っていた。

GamePresentation.cppも、表示の更新・描画の調停に加えて、被弾反応、
戦闘イベントの解釈、敵UIの配置計算、HUD、チュートリアル保存、分析JSONの
読込を同じ翻訳単位で扱っていた。
また、GameクラスのUI用モデル作成関数も表示実装と同居していた。

これらは変更される理由も必要な依存も異なるため、優先して境界を整理した。

5. 分割の判断理由

・変更理由を境界にした。
  報酬ルールの修正、ポーズ画面の調整、GPU画像の扱い、診断表示の修正は
  別々に発生する。それぞれ必要な実装だけを読み、ビルドできる位置へ移した。

・既存の状態所有者を活かした。
  RunController等が持つ状態を新しいクラスへ複製せず、Gameの既存メンバー
  関数を責任別の実装へ移した。公開APIや寿命の変更を避けながら、責任の
  所在をファイル名で辿れるようにした。

・計算と描画を分けた。
  敵UIの配置計算は、画面位置・安全領域・投影済みの敵の領域だけを入力に
  できる。EnemyInfoLayoutはGame、カメラ、GPUに依存せず、配置予約を1フレーム
  単位で保持する。配置を単独のネイティブテストで確認できるようになった。

・長い関数にも意味のある入口を作った。
  DrawFeedbackは約775行の連続処理から、次の7処理を順に呼ぶ関数にした。
  DrawScreenFlashes → DrawWorldFeedback → DrawHeavyChainBanner →
  DrawMultiDefeatBanner → DrawFloatingFeedback → DrawFeedbackDiagnostics →
  DrawShotSummary。
  描画順は維持した。敵UI関数からも配置計算とプレイヤー資源表示を抽出した。

・依存の重さも境界として扱った。
  JSONの読込は主に分析・ガイド側へ、Direct3D/WRL/stb_imageのカード・アイコン
  資源処理は専用実装へ寄せた。GameMcpBridge.hはJSONの前方宣言ヘッダーを
  使うようにした。GameBalanceConfig.cppに残っていた不要なRenderer・ImGui等の
  includeも削除した。Game.hへ重い依存を追加していない。

・同じ状態を持つGPUキャッシュは複製しなかった。
  カード画像の読込・解放タイミング、戦闘アイコンのキャッシュを維持した。
  表示部品を分けるために画像を重複読込する構造にはしていない。

6. 挙動維持の確認

移動した既存メンバー関数161定義を変更前の保存内容と照合した。
156定義は同一トークン列だった。残る5定義は次の呼出境界の整理である。

  Game::Init / Game::Uninit：カード資源の読込・解放を専用入口へ委譲。
  GamePresentation::Initialize：ガイド保存データ読込を専用関数へ委譲。
  GamePresentation::DrawFeedback：7つの描画処理へ順序どおり委譲。
  GamePresentation::DrawEnemyStatusEffects：配置計算とプレイヤー表示を委譲。

配置計算の5処理は名前の変更を除いて本体トークンが一致した。
演出7処理も、変更前の本体の連続部分と同じ順で一致した。
GameBalanceConfig.cppの変更は不要なincludeの削除と直接必要なutilityの追加。
ゲームルール、乱数の呼出順、セーブ形式、バランスデータに変更はない。

7. ビルド時間の計測

Visual Studio 2022、MSVC 14.44.35207、Debug x64、/MPを使用。
既存のtools/release_without_compiler_pdb.targetsを読み込むCodex環境用の
診断構成で比較した。通常のVisual Studioビルド設定は変更していない。
中間・出力先はResponsibilitySplitDebugへ分離した。

無変更・各差分ビルドはそれぞれ3回の中央値。各差分は対象.cppの更新日時を
変更して計測した。変更前のポーズ画面と設定参照はGame.cppにあったため、
同ファイルの差分ビルド値と比較した。

ゲーム全体の調停処理: 10.649秒 → 10.148秒（4.7%短縮）
表示全体の更新・描画調停: 10.352秒 → 7.700秒（25.6%短縮）
ポーズ画面の描画: 10.649秒 → 6.085秒（42.9%短縮）
設定値の参照: 10.649秒 → 6.162秒（42.1%短縮）
無変更：3.790秒 → 3.636秒

各差分ビルドで再コンパイルされた.cppは1個、無変更では0個である。
以前の計測資料にあった「無変更でも全ファイルが再コンパイルされる条件」
にはなっていない。

クリーンビルドは変更前後各1回の参考値：
  55.569秒 → 63.220秒（13.8%増加）
  コンパイルされた.cpp：119個 → 152個

差分ビルドの短縮を確認した一方、クリーンビルドは増加した。
翻訳単位の追加による起動・ヘッダー解析の重複が増加要因として考えられる。
これは推定であり、コンパイラ内部の時間内訳までは測定していない。
全体ビルドが高速化したという結論にはしていない。

9. 範囲と残る改善候補

今回の中心は、最大の2ファイルに混在していたゲーム調停と表示実装である。

読み取り、保存形式や判断順の回帰を確認しながら進める必要がある。

別途計測する余地がある。
